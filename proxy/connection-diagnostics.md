# 重连与大请求上传排查

先定位发生重连的具体应用、线程和时间，再确认实际传输协议与失败阶段。
`reconnecting` 是界面状态，不直接等于 WebSocket 故障、上下文超限或会话损坏。

## 证据顺序

1. 查看应用日志中的目标端点、HTTP/WebSocket transport、错误和重试间隔。
2. 从 Mihomo `/connections` 核验进程路径、域名、规则和最终节点；组名相同不保证节点相同。
3. 检查请求压缩前后字节数，以及同一连接上传/下载计数的变化。
4. 对齐内核重启、TUN 接口变化与系统重启时间。启动期间重建接口不能解释之后持续重试。
5. 进行同节点、同目标、同大小数据的 TUN/显式代理对照，尽量暂停其他上传。

只输出必要的日志字段，不公开请求体、令牌、订阅 URL、出口 IP 或线程标识。
Codex 本地日志存储及表结构随版本变化，先只读检查 schema，再按精确线程 ID 查询。
不要全文搜索所有会话后把项目内容误当成运行错误。

HTTP 握手成功只说明端点当时可达，不能验证大请求或长期流式响应。
`inProgress` 表示回合尚未结束；“另一应用打开了会话”是正常的排他锁提示。
二者均不能单独证明会话损坏，更不能据此直接修改数据库或删除会话。

## 脱敏实测：2026-09-15

环境为 Linux VM、Mihomo 1.19.29、TUN gVisor，桌面客户端中的新 Codex 会话。
日志显示 `responses_http` POST，请求压缩前 17,668,320 字节，压缩后约 12,608,989 字节。
多次出现 `error sending request`，其中连续几次失败间隔约 121–123 秒。
代理连接上传计数持续增加，返回数据很少，提示请求可能仍在上传。

使用 Cloudflare 官方测速端点，发送 2MiB 随机数据；仅临时把测速域名绑定到目标节点，
正式 OpenAI 出口不变。HTTP/1.1、清空 Expect、每次最长 55 秒，顺序执行：

| 路径 | 平均上传速度 | 总耗时 | HTTP |
| --- | ---: | ---: | ---: |
| 同地区节点 A，TUN | 54,080 B/s | 38.78s | 200 |
| 节点 A，显式 HTTP 代理 | 41,517 B/s | 50.51s | 200 |
| 同地区节点 B，TUN | 53,042 B/s | 39.54s | 200 |

按该速度，12.6MB 上传约需 233–304 秒，超过观察到的失败周期。
这支持大请求上传瓶颈假设；显式代理和第二个节点未在此次测试中改善上行。
测试时有其他会话流量，目标也不是模型端点，因此不能据此确定是 ISP、VM、代理服务商
还是端点限制，更不能宣称固定两分钟超时来自哪一层。Mihomo 字节计数不是服务端确认收包量。

下一步应在暂停重试后，比较宿主机与 VM、不同服务商或独立出口的上传。
不要把共享线路下多个节点当作独立网络。延迟测试不能替代上传测试。
截图等内容可使请求字节数增大；token 阈值不是字节数上限。压缩会话可能缓解，
但降低自动压缩阈值并不能保证解决发送超时。不要未经证实修改 stream idle timeout
来声称修复上传超时，也不要直接回放含凭据和项目数据的模型请求到测速服务。

## 当前建议

- 保留可用的 TUN + 规则模式，让核心 OpenAI 域名优先于通用进程代理规则。
- 工作时保持出口稳定；只有测速显示备用线路有改善后才切换。
- 修正已证实的规则冲突，MTU、IPv6、协议栈等参数用单变量实验验证后再改。
- 通过持久化覆写维护配置，先校验、备份，再热加载并检查内核实际规则。
  临时测试规则必须恢复；配置重载可能影响连接，不能承诺无中断。
